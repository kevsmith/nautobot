What was measured

An isolated stack on port 8180 with DEBUG=False, no Apps enabled, and pinned CPU and memory, so results reflect production-shaped code paths and every finding is attributable to core. The primary dataset is databot's enterprise-campus / large / seed 42: 24,091 objects — 2,902 devices, 8,925 interfaces, 3,278 cables, 110 locations, 595 prefixes, 2,937 IP addresses and 36,552 existing ObjectChange records, applied over REST in 1,013 seconds.

Round one ran against enterprise-campus / small / seed 42 (2,113 objects). Those numbers are kept below as history, clearly separated, because they are the reference the first four commits were measured against. Everything presented as current is large-dataset.

Three instruments, because the failure modes differ:

  • Query profiling drives each scenario through the Django test client and counts SQL. Deterministic — it repeated 2,235 → 2,235 across runs on the large dataset, which is what makes it usable as a regression gate.
  • Write-path profiling runs each operation inside a real change context and a rolled-back transaction, so change logging and signals behave as they would for a live write.
  • Wall-clock timing, in-process and over HTTP, because some costs remove no queries at all.

The workload is hand-maintained rather than auto-generated. Endpoints are named by Django view name and resolved through reverse(), and objects are selected by strategy at run time — never a baked-in primary key — so the workload survives a reseed and fails loudly if a view is renamed.

The database is not the bottleneck.

Across a full baseline run, PostgreSQL executed 325,152 queries in 4.6 seconds total — a mean of 0.014 ms each. The most-repeated query in the worst endpoint averaged 0.004 ms. Every second of user-visible latency measured here is Python-side: ORM round-trip overhead, serialization, and repeated work per object.

This has a practical consequence. Adding indexes would buy almost nothing at this scale, and the entire set of findings below is addressable in application code.

The completed work confirms it from the other direction. Across the 38 scenarios, query count fell 57% while total measured database time was unchanged — 601 ms before, 602 ms after. The 1,278 queries removed were worth almost nothing in SQL; what they cost was Python-side per-query overhead and the serialization work wrapped around them.

Findings

Ranked by measured impact, and written as they stood at the end of round one. Every one of these except F-05 has since been committed with its own clean-tree measurement — see the ledger at the foot of the page for the commit and the final number. The analysis in each card is preserved as written, including the two attributions that later measurement corrected.

F-01

Nested serializers walk foreign keys one query per hop

committedtier A + B

nautobot/core/api/views.py:263 · nautobot/core/models/__init__.py:174 · nautobot/dcim/api/serializers.py:166

Every serializer carries a natural_slug field, and computing it traverses foreign keys with plain getattr() — one SELECT per uncached hop. The viewset's prefetch logic inspects top-level serializer fields only, skipping any source containing a dot, so objects reached through nested ?depth serializers and through GenericForeignKeys are never prefetched.

The 666 repeated location queries decompose exactly: 150 interfaces are fetched cold through cable_peer and connected_endpoint; with Location.objects.max_depth == 4, 122 of them pay 5 hops and 28 hit a null parent at 2 — 122 × 5 + 28 × 2 = 666.

Reported impact: api.interface.depth1 1,332 → 435 queries, api.device.list.depth1 112 → 11, and 2,357 → 1,359 across all 38 scenarios.

F-02

Detail pages render the component tree three times

committedtier A + B

nautobot/core/templates/generic/object_retrieve.html:45, :122, :129

The detail template walks the same tab and panel tree three times — labels, table-config forms, then contents — and nothing memoizes between passes. should_render() runs three times per tab, render_label() twice, and ObjectsTablePanel.get_extra_context(), which builds and paginates a table, runs twice. A single device page issues the identical extras_contactassociation COUNT from seven distinct call sites.

This is model-agnostic, which explains why Device, Rack, Prefix and Location all show the same shape while list views — which have no tabs and no multi-pass template — stay at 9–10 queries.

Reported impact: 2,357 → 2,171 overall, with ui.device.detail 108 → 68 and ui.device.interfaces 74 → 42. Rendered HTML was diffed byte-for-byte before and after; only the CSRF token differed.

F-03

An eagerly evaluated default computes every natural key twice

verifiedtier A

nautobot/core/api/serializers.py:495 and :483

getattr(instance, "natural_slug", construct_natural_slug(instance.natural_key(), pk=instance.pk)) — Python evaluates that third argument before the attribute lookup. Since natural_slug is a BaseModel property that always exists, the fallback is computed and discarded on every row, and the property then computes natural_key() a second time. The recursive natural-key machinery reads Constance config from Redis at each level, so this cost around 3,300 Redis round-trips per request.

Making the fallback lazy removes no queries at all — which is precisely why a query-count gate alone would have missed it.

F-04

Natural-key lookups are recomputed against Redis on every access

committedtier B

nautobot/core/models/__init__.py:265 · nautobot/dcim/models/devices.py:700 · nautobot/dcim/models/locations.py:245

natural_key_field_lookups is an uncached classproperty, so it is rebuilt on every single access — and for Device and Location each rebuild performs a Constance lookup, which reads Redis. Serializing one object at depth 1 touches it dozens of times.

Profiling a 100-interface create loop: 26% of total wall time, driving 3,600 config lookups and 5,700 Redis round-trips. It costs zero SQL, which is exactly why a query-count gate cannot see it.

Memoizing for the duration of a single serialize_object_v2() call measured +19.8% on the bulk-create loop across 7 interleaved repetitions, with output verified byte-identical. Scoping to one call rather than caching on the class is deliberate: Location's value depends on live tree depth and Device's on Constance config, so a permanent cache would go stale. A permanent cache measured +21.7% — indistinguishable, and not worth the risk.

A related one-line fix: devices.py:700 calls get_settings_or_config("DEVICE_UNIQUENESS") twice in a single if/elif. Hoisting it measured +7.8% standalone.

F-05

Change logging serializes every object twice — but the redundant half is the cheap one

out of scopetier C

nautobot/extras/models/change_logging.py:45–46 · nautobot/extras/api/serializers.py:1099

to_objectchange() calls both serialize_object() and serialize_object_v2() for every change record, and deferred bulk logging does not avoid it — create_object_changes() calls the same method per object at flush time, which is why deferral saves only 6%. Ingesting this dataset created 3,219 ObjectChange records for 2,119 objects, roughly 6,400 serializations.

The measurement inverts the intuition. The redundant v1 serialization costs 0.73 ms and 2 queries; the v2 serialization that is actually consumed costs 8.75 ms and 7 queries — twelve times more. Eliminating the duplication is worth only about 8–12% of write-path wall time and 12.5% of its queries. The expensive serializer is the one that cannot be removed.

And the v1 fallback is not dead code. Migration 0022_objectchange_object_datav2 added the v2 field as nullable with no backfill, and two data migrations construct ObjectChange rows carrying only v1. So object_data_v2 is None is permanent for real historical data, and get_snapshots() genuinely depends on the fallback.

Writing {} to object_data is therefore Tier C, not the safe app-code workaround it first appeared to be. Both the REST serializer and the auto-generated GraphQL type use fields = "__all__", so the empty value would surface in two public API contracts; the ObjectChange detail panel would render an em-dash instead of JSON on every page; and four test classes in test_changelog.py assert on its contents, including test_legacy_object_data, a direct regression test for this branch.

Recorded for review rather than acted on. Pursuing it needs a deprecation cycle and a decision about pre-2022 rows whose only snapshot is v1.

F-06

One cable path is fetched three times per object

committedtier A

nautobot/dcim/api/serializers.py:169, :190, :201

Three SerializerMethodFields — connected_endpoint_type, connected_endpoint, and connected_endpoint_reachable — each call obj.cable_paths.first() independently, issuing the same query three times per serialized object. Memoizing on the instance accounts for 231 of the repeated dcim_cablepath queries in the interface endpoint.

Out of scope

Recorded, not acted on, under the agreed constraint of application code only — no migrations, indexes, schema changes, or PostgreSQL tuning.

  • Stop writing object_data (F-05). Worth 8–12% of write-path time. Changes the REST and GraphQL payloads, blanks the ObjectChange detail panel, and breaks four test classes. Needs a deprecation cycle.
  • Backfill or drop object_data. Migration 0022 added v2 with no backfill, so historical rows depend on v1 permanently. Resolving that — either backfilling v2 or making v1 nullable — is what would make F-05 tractable. Requires a migration.
  • Drop natural_slug and composite_key from nested serializers, or make them opt-in. Eliminates the F-01 cost class outright rather than mitigating it, but changes the API response payload.
  • Duplicate DeviceUniquenessValidator run. Device.save() re-runs a validator that full_clean() already executed — 2 redundant queries per Device save. It deliberately guards direct .save() callers, so removing it changes behavior.
  • get_snapshots() issues one SELECT per ObjectChange — 100 queries per 100-object bulk operation. The largest remaining SQL win on the write path after serialization. Already tracked upstream as issue #6303.
  • Index candidates: none identified. A finding rather than an omission. With 325,152 queries totaling 4.6 seconds, no query shape was slow enough for an index to matter at this dataset size.
  • Location's variadic natural key is the structural reason chains run five hops deep. Bounding it is a data-model question, not a code one.

A rejected fix worth recording

A round-one measurement, on the small dataset. Kept because the lesson is the most useful single result on this page.

One proposed change removed 666 additional queries — cutting the total from 2,357 to 1,359, a 42% reduction — and made the endpoint it targeted 62% slower.

It pre-warmed each object's natural-key foreign-key chain with a single select_related() instead of walking it hop by hop. Because Location's natural key is variadic on live tree depth, and max_depth is 4 in this dataset, that expands to eight prefixes and produces an 8-join, 5,420-character query executed once per object, joining dcim_location to itself on parent_id at every ancestor level. PostgreSQL answers it quickly, but Django then materializes wide rows across eight tables and instantiates a model object for each — costing more than the handful of primary-key lookups it replaced. It also added a per-call inspection walk to every natural_key(), which slowed a depth-0 endpoint it was never meant to touch.

What the large dataset changed about the conclusions

Query counts are page-bounded, not dataset-bounded. At 11× the data the counts barely moved, which retroactively validates the small dataset as an instrument for finding N+1s.

Two of my own conclusions were wrong and got corrected by measurement. I claimed the hierarchy endpoints scale with dataset size; page-size sensitivity testing showed that is true for exactly one of five, and the UI list endpoints are entirely fixed cost. And ui.prefix.detail appeared to regress 11% until three repeat runs produced 329 / 447 / 347ms on identical code.

Removing queries did not reduce database time. 1,278 fewer queries, and total DB time across the run went 601 ms to 602 ms. On this dataset the ORM round trip and the Python wrapped around it are the cost; the SQL itself was never in the way.

The HTTP tail is noise, and saying so is part of the result

Ranked by p95, 12 of the 38 scenarios show an increase — up to +79% on ui.status.list, a 117ms endpoint. None of that survives cross-checking: the same endpoints are flat or better on deterministic query counts, and flat in-process (ui.device.list 50.6 → 49.2ms while its p95 reads +12.8%). The p95 run was taken at concurrency 4 on a machine also running profiling work, which is the documented failure mode of this instrument. They are reported here rather than filtered out, because a table that shows only the improving rows is not a measurement.

Query count ranked the fixes in the wrong order

The single largest win removed zero queries.

Reusing nested serializers instead of rebuilding one per object is worth −28.7% on its own and changes no SQL at all. Memoizing the nav menu is worth −24% on detail pages and removes no query, no Redis read and no SQL — pure Python call overhead. On api.interface.depth1, a separately-measured change that removed 99 queries moved wall clock by +0.3%, and the rejected FK pre-warming removed 666 queries while running 62% slower.

Query count is the cheap, deterministic signal. It is the gate, not the objective.

What is next, and one retracted number

Retraction. An earlier version of this page put nav_menu at 40ms per request. That was a cProfile figure, and cProfile inflates call-heavy code — which is exactly what this was, at 12,320 has_one_or_more_perms calls per request. True wall clock was ~16ms of an ~88ms rack detail request. It has since been fixed (5b912a905, memoize the menu per request rather than per component render) and independently measured at −24% on device detail and −25% on rack detail. Never quote profiler time as wall clock.

The two follow-ups named in that earlier version are both done: the remaining 67 TemplateColumn call sites are converted (d25990a84), and the tree ancestor walk now pulls four levels per query (2e929c137).

Remaining application-code targets

  • Row-scaling N+1s that memoization cannot help. PowerFeed.utilization and the prefix hierarchy column both grow linearly with row count. Every fix on this branch so far removes repeated work; these need a different shape.
  • get_snapshots() issues one SELECT per ObjectChange — 100 queries per 100-object bulk operation, and the largest remaining SQL item on the write path now that serialization is cached. Tracked upstream as issue #6303.
  • Residual api.interface.depth1 cost is 292 queries, down from 1,229. What is left is GenericForeignKey destination fetches and reverse one-to-one device-bay lookups on the nested Device serializer — the same mechanism as the accepted fixes, not yet applied to those two paths.
  • api.prefix.list spends 13.7ms planning a query that executes in 1.3ms, re-planned every request — about 21% of that endpoint's time. Explicitly not an index: an index makes planning worse. The lever is prepared-statement reuse or narrowing the serializer's select_related fan-out.

Two things worth more than the next code fix

The largest measured gap is environment, not code.

Against next.demo.nautobot.com at the same API version: /api/dcim/devices/?limit=50 takes 1,051ms there versus 231ms unpatched here, and /api/ipam/prefixes/?limit=100 — an endpoint this branch barely changes, 58 → 55ms — takes 274ms, 4.7× slower. That control isolates the difference as environment. TLS handshake was ~70ms, so it is not the network. The parity checklist in perf/README.md lists what has to match; its first two questions (shared vs dedicated vCPU, steal time under load) may settle it without building a replica.

Coverage is ~5%. 38 hand-picked scenarios against a surface of 330 API list endpoints, 320 detail endpoints and 127 UI list views. api.interface.depth1 — now a 76% query reduction and a 74% p95 reduction — was found by guessing that interfaces is the biggest table. A screening pass over reads for every model, normalized to cost per object, is designed in perf/README.md and not yet built. It is a ranking instrument, not a gate; the inner loop stays at 38 scenarios.

The gate is availability: an endpoint that returned 200 or 302 at baseline must not start erroring or 404ing. Content and row ordering may change and are reported for information only. Every accepted commit also records its risk tier — A (no observable behavior change), B (result-preserving but subtle, usually a new cache scope), C (changes observable behavior; measured, not shipped).

Caveats

  • The full test suite has never completed on this branch. Targeted tests pass throughout — including dcim.tests.test_api (1,673) and ipam.tests.test_views (596) — but the one whole-suite attempt died in Django's parallel runner with a pickling error and exited 0. This is the gating item before any of it becomes a pull request; run invoke tests --no-parallel. Note also that test_get_docs_url fails across ~35 dcim model tests whenever --skip-docs-build is passed, on a clean tree too.
  • No changelog fragments and no docs yet. 33 files of core changes, including a new public export (nautobot.apps.tables.TemplateColumn) that needs documenting. The fragments in changes/ belong to unrelated develop work.
  • Wall clock on this machine needs three alternating rounds. Two were twice not enough: a 2ms and an 11% "regression" both dissolved on a third round. Four commits quote no wall-clock number at all because the box was under concurrent load; their evidence is a deterministic counter. Any single-round timing figure on this page should be read as directional.
  • No full write-path re-run at HEAD. The last complete Tier 1W run predates the final two commits; the config-read figures for update, delete and create.interfaces.x50 come from the A/B arms of 5f351dc5b rather than from one clean sweep.
  • HTTP p95 predates the last two fixes and was captured at concurrency 4 on a loaded machine. It is the weakest instrument here and the 12 apparent regressions in its tail are noise, cross-checked against deterministic counters.
  • Improvements are not additive. Several changes reduce natural-key work by different means, so their individual gains overlap rather than sum. Only the cumulative row is a sum.
  • Small-dataset history. The round-one section measures 2,113 objects, where most list views paginate at 25–50 rows and look fast regardless. Those figures are kept for provenance, not for judging real-world value.
  • Silk middleware remains in the request chain. It is inert without a session flag and constant across runs, so it does not distort relative comparisons, but it is present in every absolute number here.
  • UI response bodies are not byte-stable between identical requests, so HTML endpoints are compared on query count and status rather than content.
